## Statement

As a platform maintainer, I want to build a modular backlog automation system with vendor adapters, structured scanning, and configurable subject resolution so that evidence generation is reliable, testable, and extensible across multiple forge platforms.

## Context

Current implementation:

- GitHub-specific logic embedded in `lib/work-management/index.ts`
- Subject extraction fails silently (evidence generation gaps)
- Automation orchestration mixed into workflow Python scripts (untestable, unmaintainable)
- No structured error reporting (difficult to debug failures)
- Cannot be reused in other CI/CD systems

Desired implementation:

- Vendor-agnostic domain logic behind provider adapter interface
- Multi-strategy subject resolution with fallback chain
- Separate scan phase (read-only) from evidence generation (write)
- Structured JSON reports for audit and metrics
- Testable without GitHub Actions environment

## Goals

- Define and implement `BacklogAutomationProvider` interface
- Extract GitHub-specific logic into `GitHubBacklogAutomationProvider`
- Implement multi-strategy `SubjectResolverChain` with configurable order
- Build `BacklogScanExecutor` and `ScanReporter` for structured reporting
- Add `backlog scan` CLI command with evidence generation option
- Update workflows to use CLI instead of embedded Python
- Support vendor configuration through `automation.subjectResolutionOrder` config

## Acceptance Criteria

- [ ] `BacklogAutomationProvider` interface and `GitHubBacklogAutomationProvider` created
- [ ] Subject extraction logic extracted to provider method
- [ ] PR metadata fetching available via provider (for resolver fallback)
- [ ] `SubjectResolver` interface and strategy implementations complete
- [ ] `SubjectResolverChain` executor tries strategies in configurable order
- [ ] `BacklogScanExecutor` orchestrates parsing, condition checking, resolution, reporting
- [ ] `ScanReporter` generates valid JSON and human-readable text output
- [ ] `backlog scan` CLI command works with flags: `--generate-evidence`, `--report-format`, `--resolver-order`
- [ ] Evidence generation is optional (default: report-only)
- [ ] Evidence records created when `--generate-evidence` flag set
- [ ] All scan decisions and errors visible in JSON report
- [ ] Workflows use CLI command; Python scripts removed
- [ ] Config supports `automation.subjectResolutionOrder` with enum values
- [ ] All core logic tests pass (no GitHub Actions required)
- [ ] User documentation updated with new scan terminology and config
- [ ] Subject resolution failures include clear guidance (strategy used, fallback attempts)

## Implementation Approach

### Layer 1: Provider Abstraction (Phase A)

Define `BacklogAutomationProvider` interface and extract GitHub-specific payload parsing:

```typescript
interface BacklogAutomationProvider {
  parsePayload(raw: Record<string, unknown>): ParsedEvent;
  extractPRIdentity(event: ParsedEvent): PRIdentity | null;
  extractWorkflowRunIdentity(event: ParsedEvent): WorkflowRunIdentity | null;
  normalizePRReference(ref: string): string;
  fetchPRMetadata?(identity: PRIdentity): Promise<PRMetadata | null>;
}
```

### Layer 2: Subject Resolution (Phase B)

Implement resolver strategies that try multiple approaches:

```typescript
interface SubjectResolver {
  name: string;
  resolve(
    event: ParsedEvent,
    provider: BacklogAutomationProvider,
  ): Promise<SubjectResolutionResult>;
}

class PayloadSubjectTokensResolver implements SubjectResolver {
  // Extract work-item:... tokens from PR body, title, workflow name
}

class LinkedPullRequestsResolver implements SubjectResolver {
  // Fetch PR metadata via provider; search PR body for tokens
}

class AuditPRSubjectIndexResolver implements SubjectResolver {
  // Query audit index for historic subject associations (future)
}
```

### Layer 3: Scan Orchestration (Phase A & C)

Coordinate parsing, condition checking, resolution, and optional evidence creation:

```typescript
class BacklogScanExecutor {
  async execute(events: Record[], options: ScanOptions): Promise<ScanReport> {
    // For each event:
    //   1. Parse via provider
    //   2. Extract identities
    //   3. Resolve subject via resolver chain
    //   4. Evaluate conditions (pr_merged, workflow_succeeded, subject_resolved, etc.)
    //   5. Optionally create evidence records
    //   6. Build event report with all decisions and errors
  }
}
```

### Layer 4: CLI and Workflow Integration (Phase D)

Replace Python workflow scripts with CLI:

```bash
# Report only (default)
doc-vader backlog scan --report-format json > report.json

# Report + create evidence
doc-vader backlog scan --generate-evidence --report-format json

# Custom resolver order
doc-vader backlog scan --resolver-order payload_subject_tokens,linked_pull_requests
```

## Phased Rollout

**Phase A**: Core scan command and report generation (no behavior change; read-only)
**Phase B**: PR-link resolver and full condition taxonomy
**Phase C**: Evidence generation mode (opt-in)
**Phase D**: Workflow conversion (thin wrapper around CLI)
**Phase E**: Configuration support and strict mode

## Testing Strategy

- Unit tests for each resolver strategy (mock provider)
- Integration tests for `BacklogScanExecutor` (mock events + mock provider)
- CLI command tests (invoke with test fixtures)
- Evidence creation tests (verify records created, linked correctly)
- Backward compatibility tests (verify current behavior preserved until Phase C)

## Success Metrics

- 100% of automation core logic covered by unit tests
- Zero silent failures (all failures logged with reason in report)
- Evidence generation success rate increases by >10% (templ.js incident resolved)
- New resolver strategy can be added in <1 hour
- Backlog scan report provides actionable debugging info for all errors

## Risks

- **Latency**: PR metadata fetching may slow down evidence generation (mitigated by optional flag)
- **Rate limiting**: Aggressive PR fetching could hit vendor API limits (mitigated by caching + strategy config)
- **Backward compatibility**: Workflow changes may break existing automation (mitigated by thin wrapper that preserves behavior)
