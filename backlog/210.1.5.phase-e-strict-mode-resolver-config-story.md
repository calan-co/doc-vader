## Statement

As a backlog manager, I want to configure subject resolution strategy order and optionally run scans in strict mode so that I can control resolver fallback behavior and fail fast when conditions are not met.

## Context

Phases A-D build the core scan infrastructure. Phase E adds configuration options that let users tune resolver behavior per consumer and optionally enforce stricter validation. This enables:
- Fast scans (payload-only resolver) for time-sensitive workflows
- Comprehensive scans (full resolver chain) for automated linking
- Strict mode to fail if expected conditions not met (catch configuration errors early)

## Goals

- Add `--resolver-order` CLI flag to override default resolver chain
- Add `--strict` CLI flag to exit with error if conditions not met
- Support `automation.subjectResolutionOrder` in `.doc-vader/backlog-consumer.json`
- Document configuration options and use cases

## Configuration Options

### Resolver Order

```json
{
  "automation": {
    "subjectResolutionOrder": [
      "payload_subject_tokens",
      "linked_pull_requests",
      "audit_pr_subject_index"
    ]
  }
}
```

### CLI Usage

```bash
# Use custom resolver order
doc-vader backlog scan --resolver-order payload_subject_tokens

# Strict mode: fail if any errors
doc-vader backlog scan --strict

# Combine options
doc-vader backlog scan --resolver-order payload_subject_tokens,linked_pull_requests --strict --generate-evidence
```

## Resolver Strategy Reference

| Resolver | Speed | Coverage | Requires | Use Case |
| --- | --- | --- | --- | --- |
| `payload_subject_tokens` | Fast ⚡ | Basic | None | Time-sensitive workflows; subjects always in payload |
| `linked_pull_requests` | Medium ⚡⚡ | High | GitHub API | Comprehensive scans; subjects may be in PR metadata |
| `audit_pr_subject_index` | Medium ⚡⚡ | Lookup | Audit index | Subjects may have been added historically |
| `provider_associated_pull_requests` | Medium ⚡⚡ | High | Vendor API | Vendor-specific; delegates to provider |
