## Statement

As a maintainer, I want to refactor backlog automation to support multiple forge providers, implement robust subject resolution, and provide structured, auditable scan reporting so that evidence generation is reliable, testable, and extensible.

## Context

Current backlog automation tightly couples GitHub-specific logic with domain logic. Subject extraction fails silently, creating blind spots in evidence generation. Automation logic is embedded in workflow Python scripts, making it difficult to test, reuse, or enhance.

## Goals

- Abstract vendor-specific logic behind a provider interface
- Implement multi-strategy subject resolution with structured error reporting
- Separate scan phase from evidence generation for safety and clarity
- Enable testing of automation logic outside GitHub Actions
- Provide structured JSON reports for audit and monitoring
- Support future forge providers without core changes

## Acceptance Criteria

- [ ] `BacklogAutomationProvider` interface defined and GitHub adapter implemented
- [ ] Multi-strategy `SubjectResolver` implemented with configurable chain
- [ ] `BacklogScanExecutor` and `ScanReporter` implemented with structured output
- [ ] `backlog scan` CLI command works with `--generate-evidence` flag
- [ ] Evidence generation is opt-in and separately reportable
- [ ] Workflows refactored to use CLI command instead of embedded Python
- [ ] All core logic unit tested (no GitHub Actions required)
- [ ] User documentation updated with new scan terminology and config options
- [ ] Subject resolution failures visible in scan reports with clear guidance

## High-Level Architecture

The implementation follows a layered approach with clear separation of concerns:

- **Adapter Layer**: Vendor-specific payload parsing and metadata fetching
- **Domain Layer**: Vendor-agnostic event processing, condition checking, subject resolution
- **Scan Layer**: Event orchestration, report generation, evidence coordination
- **CLI Layer**: User-facing commands, flag parsing, report serialization

## Success Metrics

- Zero silent failures in evidence generation (all failures logged with reason)
- Evidence generation success rate increases from current baseline (templ.js incident resolved)
- All automation tests pass without GitHub Actions environment
- New vendor adapter can be added with <50 lines of code
- Scan report provides actionable debugging information for 100% of failures

## Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| Latency increase from PR metadata fetching | Multi-strategy chain defaults to payload-only; PR fetch is optional fallback |
| Rate limiting on vendor API calls | Implement caching; configurable strategy order to limit API usage |
| Complexity of resolver chain | Clear documentation; extensive tests; debug mode shows resolver attempt log |
| Breaking changes to scan report schema | Semantic versioning; migration guide in documentation |
