## Statement

As a platform architect, I want to research refactoring `doc-vader` into a core, modular linting and validation framework and clarify the scopes of `doc-vader`, `linkity`, and `backlogger` so that duplication is reduced and future policies/extensions can be isolated cleanly.

## Context

Recent duplicate file cleanup highlighted overlapping responsibilities between `doc-vader` (linting/validation scripts), `linkity` (link + decision docs), and `backlogger` (work-item/frontmatter lint + hooks). Centralizing shared linting primitives (rulesets, parsing, frontmatter schema integration) inside `doc-vader` as a "core" would allow the other packages to depend on stable interfaces instead of copying logic. This spike will define boundaries, shared contracts, and a phased extraction plan.

## Actors

- **Primary:** Platform Architect
- **Secondary:** Documentation Maintainer, Tooling Engineer

## Goals

- Inventory current linting & validation code paths in all three packages.
- Define a clear responsibility matrix (ownership boundaries) for `doc-vader`, `linkity`, `backlogger`.
- Identify candidate shared interfaces (Ruleset registry, Frontmatter schema loader, File graph utilities).
- Produce proposed modular folder layout for `doc-vader` core vs package-specific adapters.
- Outline phased migration plan (low-risk sequence, dependency updates).

## Preconditions

- [ ] Access to all three repositories/packages and current CI workflows.
- [ ] Ability to run existing lint / validation scripts locally.

## Steps

1. Catalog existing linting/validation entry points and duplicate modules.
2. Map responsibilities into a RACI-style matrix (per concern: parsing, schema, graph, backlog templates, link resolution).
3. Draft shared interface definitions and extension points (TypeScript types + optional plugin loader concept).
4. Propose new `doc-vader` core layout and adapter structure.
5. Assess migration impact, risks, and required CI changes.
6. Produce spike summary + recommendation.

## Outcomes

A written spike summary including: responsibility matrix, interface sketches, proposed folder/module layout, phased migration plan, and risk assessment with mitigation strategies.

## Acceptance Criteria

- [ ] Responsibility matrix clearly separates concerns (no ambiguity per feature).
- [ ] List of duplicate modules with recommended consolidation path.
- [ ] Interface sketches (TypeScript) for core services (ruleset registry, schema loader, graph analyzer).
- [ ] Proposed folder / package layout approved by stakeholders.
- [ ] Phased migration plan with effort estimates and risk tags (low/med/high).
- [ ] Spike document stored in `doc-vader/docs/architecture/` or appropriate planning folder and linked from this story.

## Notes

Consider externalization of backlog-only logic (template compliance, work-item precedence) into `backlogger` consuming a published `doc-vader` core. Evaluate whether `linkity` can rely solely on core graph + link validation without bundling schema logic. Investigate plugin model for adding future documentation policies without modifying core.
