## Problem

Current sweep/ingest flow is event-driven per merged PR. If a work item has multiple linked PRs,
one merged PR can trigger finalization as soon as other finalize prerequisites are present.

This can close a work item before all linked implementation PRs are merged.

## Correctness Goal

A work item should be finalized only when all linked PRs in the work item frontmatter are merged.

## Clarified Non-Circular Flow

1. Locate candidate work items by status (`ready-for-review` or `in-progress`).
2. Read linked PR URLs from each work item's existing frontmatter (`links.pull_requests`).
3. Resolve merge state for each linked PR.
4. Mark item eligible only if every linked PR is merged.
5. For eligible items, run finalization (subject-targeted) with existing evidence/actual safeguards.

Note: ingest/sweep may still add missing PR links and commit evidence, but eligibility for finalization must evaluate the full linked PR set as currently stored on the work item.

## Acceptance Criteria

- [ ] Finalization path checks all linked PRs from `links.pull_requests` before closing.
- [ ] If any linked PR is unmerged/open, item is not finalized.
- [ ] If `links.pull_requests` is empty, item is not finalized.
- [ ] Existing safeguards remain enforced: subject targeting, evidence required, actual effort required.
- [ ] Dry-run output clearly reports blocked reason when finalization is skipped due to unmerged linked PRs.
- [ ] Add tests for single-PR merged, multi-PR all-merged, and multi-PR partial-merged scenarios.

## Implementation Notes

- Keep the identity guard unchanged: no mutation without explicit resolved subject.
- Keep subject-resolution behavior unchanged in this story (identity plumbing is tracked separately from finalization policy).
- Avoid relying on synthetic payload fields for eligibility decisions; use canonical work-item frontmatter state for linked PR completeness.
- Ensure repeated sweep runs are idempotent and do not oscillate status.
